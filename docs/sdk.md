# SDK, versioning, and deprecation policy

This document implements the SDK part of `docs/architecture.md` section 12 (work package E4 in
`docs/plan.md`): the OpenAPI document is the source of truth, SDKs are generated from it, and
integrators get a signing helper, a runnable Python example, a sandbox, and the policy below.

## What ships

| Artifact | Location | Notes |
|---|---|---|
| OpenAPI 3.1 document | `crates/topup/openapi.json`, served at `GET /openapi.json` | Generated by `utoipa`; a snapshot test fails when the code and the file drift. |
| Generated Python client | `sdk/python/src/topup_client` | `make -C sdk/python generate`; never edited by hand. CI regenerates it and fails on any diff. |
| Python SDK layer | `sdk/python/src/topup_sdk` | RFC 9421 signing and verification, Standard Webhooks verification, address and deposit-id recomputation, idempotent retrying client. |
| Integration example | `sdk/examples/phala_cloud_integration.py` | Pins the settlement key, registers an account, recomputes its addresses, quotes, lists deposits, and verifies settlement requests and webhooks; runs against the sandbox. |
| Reference product | `deploy/product/reference_product` | The staging product: settlement endpoint (all six obligations, conformance-tested), webhook receiver, and account API (`serve`), and a deposit driver (`deposit`); runs end to end against the sandbox and staging. |
| Sandbox | `deploy/sandbox/` | Sepolia overlay, capped route, credential issuance, scripted scenarios. See its README. |

The Python distribution is `crypto-topup-sdk` (Python 3.12 or later). Runtime dependencies are
bounded to their tested major version in `pyproject.toml`; `sdk/python/uv.lock` pins every
package, including the generator and lint tools, to exact versions and hashes.

## Signing profile

Product requests are signed with RFC 9421 HTTP Message Signatures using ed25519:

- covered components, in this order: `"@method"`, `"@target-uri"`, `"content-digest"`, and
  `"idempotency-key"` only when that header is sent;
- `Content-Digest: sha-256=:<base64>:` over the exact body bytes, also for empty bodies;
- parameters `created` (Unix seconds, accepted within five minutes of the service clock) and
  `keyid`, optionally `alg="ed25519"` and `nonce`, serialized as RFC 8941 structured fields;
- `@target-uri` is `scheme://host[:port]/path?query` exactly as sent. The service rebuilds it
  from its configured public origin (`TOPUP_PUBLIC_ORIGIN`) and the request path and query, so
  the client's base URL must be that public origin; a default port is omitted.

Each signature is accepted once. Because ed25519 signatures are deterministic, two identical
requests signed in the same second would carry the same signature, so the SDK adds a random
128-bit `nonce` to every signature and keeps `created` at the clock; it still retries
`409 signature_replayed` with a new signature. The verifier covers every parameter through the
serialized `@signature-params`, so the nonce needs no server support.
`crates/topup/tests/fixtures/rfc9421-python-signer.json` holds requests signed by the Python SDK,
one with a nonce; the Rust verifier test in `crates/topup/src/api/auth.rs` verifies them, and the
Python tests require the signer to reproduce them byte for byte.

The same profile, with `idempotency-key` always covered and `keyid = settlement/v1`, signs the
service's settlement requests to products; `topup_sdk.verify_request` verifies them against the
receiver's configured public URL. `crates/adapters/tests/fixtures/rfc9421-rust-settlement.json`
holds a POST and a `GET` by key signed by the service's `SettlementClient`; a Rust test keeps it
current and the Python tests verify it.

Webhooks use the Standard Webhooks asymmetric `v1a` scheme with the same settlement key;
`topup_sdk.verify_webhook` verifies them. Pin the settlement key only after verifying the
attestation (`GET /v1/attestation`, section 14 of the architecture). `TopupClient.attestation`
checks that `report_data` binds the nonce, the settlement key, and the listed flusher operators
(`topup_sdk.verify_attestation_binding`); the quote itself still needs the official dstack
verifier (`deploy/dstack-verifier.sh`, deploy/README.md "Attestation, ingress, and egress"), whose
verified report data must be `report_data` zero-padded to 64 bytes.

## Versioning

### API

- The path prefix carries the API major version (`/v1`). Within a major version every change is
  backward compatible: new endpoints, new optional request fields, new response fields, new
  error codes, and new event types. Clients must ignore unknown response fields and unknown
  event types.
- A breaking change requires a new path prefix (`/v2`). The old prefix keeps working for the
  full deprecation window below.
- `info.version` in `openapi.json` is the service release version (the Cargo workspace
  version) and follows SemVer measured on the published contract: MAJOR with a new path prefix,
  MINOR when the OpenAPI document gains anything, PATCH when the document is unchanged or only
  descriptions change.
- The settlement payload and webhook envelopes carry their own contract: settlement payloads
  have `"version": 1`, and products must refuse versions they do not implement. A new payload
  version is announced and sent only to products that opted in.

### SDK

- `crypto-topup-sdk` follows SemVer independently of the service. MAJOR for any breaking change
  to the public Python API (`topup_sdk` exports and generated `topup_client` names), or support
  for a new API major version; MINOR for regeneration against an additive OpenAPI change or new
  helpers; PATCH for fixes that change no public signature.
- Each release records the `info.version` of the OpenAPI document it was generated from.
- Only `make -C sdk/python generate` changes `src/topup_client`; the CI job
  `sdk` fails if regeneration is not a no-op, so a service PR that changes `openapi.json` must
  regenerate the client in the same PR.

## Deprecation

- Anything integrators use can be removed only after a deprecation window of at least 90 days,
  counted from the announcement: endpoints, request or response fields, error codes, event types
  or fields, settlement payload versions, SDK public functions and parameters, and API major
  versions.
- Announcing a deprecation means, in one release: marking the element `deprecated: true` in
  OpenAPI (and emitting `DeprecationWarning` from the SDK), adding a `Deprecated` changelog entry
  with the earliest removal date, and notifying every registered product contact.
- Removal happens in the sandbox first and in production no earlier than the announced date.
- Only a security fix may shorten the window; the changelog entry must say so and why.

## Changelog rules

`sdk/python/CHANGELOG.md` follows the Keep a Changelog layout:

- every pull request that changes `openapi.json`, `topup_sdk`, the generated client, or the
  signing profile adds an entry under `Unreleased`;
- entries go under `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, or `Security`;
- a release heading carries the SDK version, the release date, and the OpenAPI `info.version`;
- a `Deprecated` entry names the replacement and the earliest removal date; a `Removed` entry
  links the release that deprecated it;
- breaking changes are listed first and repeated in the release summary.

## Development

```sh
make -C sdk/python sync      # uv sync --locked --all-groups
make -C sdk/python check     # ruff, mypy --strict, pytest, and the regeneration no-op check
make -C sdk/python generate  # after an openapi.json change
```

Regenerate the interoperability vectors only after an intentional profile change, then rerun the
Rust test:

```sh
(cd sdk/python && uv run --locked python -m tests.vectors)
cargo test -p topup --lib api::auth
```
